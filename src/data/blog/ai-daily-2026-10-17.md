Songv 分享的这个 agent 引起我注意，不是因为它能做什么，而是因为它很小。核心代码 200 行，不依赖 ReAct 或 RLM 这类现有范式，移植到 iOS 之后能把自己变成任意 App，接上 ESP32 传感器可以按需变成温度计或软路由。他的核心判断是：**模型越强，人类约束反而成为新瓶颈**。

这个判断值得仔细想一下。

## 约束在哪里转移

过去设计 agent 框架的主要动力是弥补模型能力不足。ReAct 把推理步骤和工具调用交替编排，目的是让模型在能力有限的条件下仍能完成多步任务。框架越复杂，往往说明设计者对模型的信任程度越低，需要用结构来托底。

200 行的极简实现暗示的是另一个方向：如果模型足够强，大量的框架代码本质上是人为写死的约束，不是能力，是上限。工具定义、调用顺序、失败重试逻辑，这些一旦硬编码进去，模型就只能在这个框子里转。能自变工具的设计反过来，把工具定义本身交给模型动态生成，框架退化成一层薄薄的执行壳。

这种转移有一个明确的适用前提：模型在任务上下文理解和工具设计上要达到足够可靠的水准。否则"自变工具"只会把错误放大。Songv 的案例里模型用的是当前较强的版本，这是条件，不是结论普遍成立的保证。

## 200 行的实际含义

代码行数本身当然不是指标，但在这个上下文里它是一个信号：实现里没有太多边界情况处理、没有复杂的状态机、没有多层错误恢复逻辑。这意味着设计者接受了一定程度的不可控性，将这部分责任交给模型而非框架。

我的判断是，这种设计在探索型任务上有真实优势，在对可靠性要求高的生产场景里代价尚不清楚。训练猫脸分类器或做游戏原型，失败的代价是重跑一次；如果用在接触真实数据或外部接口的任务上，动态生成的工具定义可能带来难以预期的行为。

"人类约束成为瓶颈"这个说法是准确的，但瓶颈和安全边界有时候是同一件东西，只是立场不同。去掉框架约束之前，值得先问清楚：这个任务里允许模型做哪些我没有预想到的操作？

## 如何判断自己的场景适不适合

一个简单的核验思路：如果任务的目标可以用"尝试、观察、调整"的循环来推进，并且每一步的输出都可以人工介入，极简 agent 的设计会比复杂框架更顺手。因为复杂框架的价值在于批量可靠，不在于灵活探索。

如果任务要求每一步行为都在预定义的范围内，或者错误代价高到不能事后补救，那么"自变工具"带来的不可预期性就不是灵活性，而是风险。

Songv 没有公开完整代码，目前只能从描述和演示视频里判断设计思路。后续是否适合移植到自己的项目，还需要看实际的工具生成质量和失败模式，而不是先被 200 行这个数字说服。
