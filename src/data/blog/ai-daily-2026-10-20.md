Yelp 这条消息值得认真对待。据 Solidot 的报道，Yelp、达美航空、摩根大通、嘉信理财、亚马逊等平台已证实屏蔽或限制 OpenAI、Meta、xAI 等公司智能体的访问。Yelp 的表态最明确：只允许付费参与数据许可计划的智能体进入，没有授权合作的一律拒绝。

[![来源配图：多平台屏蔽AI智能体](https://icon.solidot.org/images/topics/topicinternet.png?123)](https://m.okjike.com/originalPosts/6ad63603bd0563695b265feb)

这件事的实际含义比"平台壁垒"这个词描述的要具体。构建 Agent 产品时，能力边界通常被描述成"能访问哪些工具"，即工具调用范围、上下文长度或模型推理质量。但这次暴露的是另一种限制：目标平台在协议层面直接拒绝入站，而不是功能层面的约束。无论 Agent 的推理能力多强，HTTP 请求在授权验证阶段被拦下，后续一切都不会发生。

这两种限制的处理方式完全不同。功能层面的限制可以通过改提示词、换模型、加工具来改善；协议层面的拒绝只能通过商业谈判或购买平台许可计划来解决，不是工程问题。把协议问题当功能问题来调试，会白费大量时间。

---

## 先查授权，再评工具

我的判断是：在评估一个 Agent 产品能否用于某个场景之前，值得先确认目标平台是否已屏蔽你依赖的 Agent 框架或模型提供商。具体可以检查两处：目标平台的开发者文档或 ToS 里有没有关于自动化访问的限制条款，以及该平台有没有公开声明屏蔽特定 AI 公司的爬取或 API 调用。

这个核实成本很低，但能帮你在早期过滤掉一整类"技术上可行、商业上走不通"的方案。

另一个值得同步考虑的是 token 成本的压缩空间。headroom 这个开源工具声称对 JSON 输入可压缩 60–95% 体积、为编码 Agent 减少约 20% token 消耗，提供库、Agent 和 MCP 服务器三种接入形式。假设你的 Agent 大量处理结构化工具返回值（API 响应、数据库查询结果），在进入模型之前先做一层压缩，账单变化是可以直接量化的。但这个收益的前提是平台本身能访问，否则压缩效率再高也解决不了入口被封的问题。

## 关于意图扩展的那个报道

Anthropic 据报正在测试一个新模型，内部知情人描述了两个特点：给出少量信息它能推断真实目标，修 bug 时可能主动找到并询问是否一起修同类问题。这是单一知情人的描述，上线时间和名称均无官方确认。

但这个方向本身值得单独思考一下。如果模型开始主动扩大修改范围，对使用者来说是双刃剑。好处是减少来回确认的轮次；坏处是模型推断的"真实目标"可能与使用者实际意图存在偏差，而且偏差发生在执行阶段，不是在计划阶段。意图推断越激进，使用者对每一次调用的结果就越难预期。

对于需要精确控制修改范围的工程任务，这一点尤其需要注意。
