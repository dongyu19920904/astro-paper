Grok Bot 最近被演示了一件事：内容收集、写代码、视频渲染，三个环节全部在 Grok 的云端虚拟机里完成，本地不需要运行任何进程。开发者歸藏在即刻发布了实测贴，并同步公开了提示词，替换用户名即可复用。

这个演示值得多看一眼，因为它触及的不是"AI 能不能做视频"，而是一个工程问题：自动化链路的执行环境放在哪里。

## 执行环境在哪里，决定了维护代价在哪里

传统的内容自动化脚本通常依赖本地环境：Python 版本、依赖库、ffmpeg、网络代理，任何一项变动都可能让定时任务静默失败。你可能周一发现早报没出，回头检查才发现是某个库的版本冲突，或者本机睡眠策略把进程打断了。

全云端方案将这层维护代价转移给了平台。Grok 的云端虚拟机负责保持环境一致，任务失败的排查入口也在同一个地方。对于只想稳定跑出早报、不想维护本地环境的开发者，这个转移是实质性的好处。

但转移不等于消除。云端方案引入了另一类依赖：平台的 token 额度、接口稳定性、虚拟机的可用时段。歸藏在另一条帖子里提到，他用的是闲置 Code plan 额度配合 Grok Bot 调用，并明确标注这是个人实验，接口稳定性需要自行评估。这是诚实的边界说明，值得照单全收：全云端意味着你不再担心本地环境崩溃，但要接受平台策略变更时链路整体失效的风险。

## 提示词公开意味着什么

歸藏公开提示词这件事本身也有意思。视频早报的自动化链路，拆开来看是几个可分解的子任务：从哪里收集内容、按什么结构写摘要、调什么工具渲染视频。提示词公开之后，复用门槛从"会写提示词"降到了"会替换变量"。

这对想试的开发者是好事，但也值得注意一个前提：歸藏的演示是在特定账号权限和额度配置下跑通的。提示词本身能告诉你任务逻辑，但不能保证在你的账号下同样可用，尤其是涉及 Code plan 额度的部分。我的建议是先在小规模内容上验证链路是否跑通，再接入真正的生产节奏。

## Codex 新增手机控制插件

同日还有一个值得记录的变化：开发者钟二信发布了 iPhone-use 插件，演示了 Codex 操控 iPhone 真机完成刷朋友圈、淘宝下单、发小红书等操作，项目已开源。

这两件事放在一起，方向是一致的：AI Agent 的执行范围在向外扩，从文本生成扩到云端进程调度，再到手机界面操作。执行能力增加之后，评估的重点也应该随之转移，从"它能不能做"变成"我在哪个环节还保有核查和中止的手段"。

全云端早报和手机控制插件都是开发者个人实验，不是成熟产品功能。现在去试，得到的是方向感和早期反馈，不是生产稳定性保证。
