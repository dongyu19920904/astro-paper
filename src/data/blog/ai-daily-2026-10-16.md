千问办公显示 Agent 执行了多少秒，云帆在即刻吐槽这件事。他的判断是：这将工程焦虑转嫁给了用户。其他工具只显示"正在生成"，实时读秒反而让人更关注速度本身，而不是结果对不对。

[![来源配图：xerj-org/xerj: 为 AI 搜索数据建立自动索引 · README 展示图](https://raw.githubusercontent.com/xerj-org/xerj/main/docs/media/demo-poster.png)](https://github.com/xerj-org/xerj)

这条吐槽值得认真想一想。进度显示不是中性的设计。它暴露了什么，就会让用户去盯什么。Agent 跑了 37 秒还没结束，用户的第一反应不是"结果会不会准"，而是"是不是卡住了""要不要重新发"。这种感受和任务质量无关，却会直接影响用户对工具的判断。

反过来说，隐藏进度也不是万能解法。如果 Agent 确实会跑很久，完全不提示反而让用户更不安。更合理的设计可能是分层：告诉用户"正在处理，预计需要一点时间"，而不是精确到秒地播报每一步耗时。把过程透明化和把等待时间数字化，是两件不同的事。

---

同一天出现的 xerj 索引工具，在解决一个性质相近的问题。

Agent 在处理大量代码、日志或文档时，默认行为往往是逐行 grep 或把整份文件塞进上下文，Token 消耗随内容量线性增长。xerj 的做法是提前为这些数据建立索引，让 Agent 按需检索，而不是每次都全量扫描。官方数据是使用的 Token 比 grep 少 40 倍，兼容 Elasticsearch，现有客户端可以直接接入。

40 倍这个数字我没有独立测试过，但它背后的逻辑是成立的：索引查询的代价是固定的，全文扫描的代价随规模增长。对于频繁检索大量非结构化数据的场景，建索引是合理的优化方向，不是什么新发明，只是之前很少有人专门将它做成 Agent 友好的接口。

进度条和 Token 消耗，表面上是两个不同的话题，但背后是同一个问题：Agent 执行过程中的资源和时间是否应该被直接暴露给使用者？

对用户来说，暴露秒数制造焦虑；对开发者来说，暴露 Token 占用帮助优化。DeepSeek Harness 的 dsh-context 插件走的是后一条路，将上下文按步骤展开，显示每部分的 Token 占用和工具调用情况。这类工具的目标受众是搭建 Agent 的人，而不是使用 Agent 的人。同样是"让过程可见"，服务对象不同，设计逻辑就相反。

我的判断是：Agent 类产品的进度透明度设计应该分两层。面向终端用户，隐藏技术细节，给出状态而非数字；面向开发者，尽量让执行路径和资源消耗可查。把工程监控界面直接对着普通用户，大概率适得其反。

如果你正在搭建 Agent 工作流，xerj 和 dsh-context 这两个工具值得看一下，前者减少不必要的上下文输入，后者帮你找到已有上下文里哪部分占得多。两者都是在解决"Agent 吃 Token 没有节制"这个实际痛点，适用条件是你的任务已经复杂到上下文开销成为瓶颈。规模还小的时候，优化这里的收益有限。
