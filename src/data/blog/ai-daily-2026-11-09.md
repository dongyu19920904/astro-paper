一个新工具放出来，README 上说"欢迎试用"，于是有人直接搬进了生产环境。然后发现某个接口悄悄改了，配置方式也变了，集群里原本运行的任务开始出错。这种事不是哪家工具独有的麻烦，但"预览版"这三个字具体意味着什么，值得停下来想清楚。

NVKE 是 dsx-ai-factory 在 GitHub 公开的一个项目，全名 NVIDIA Kubernetes Engine，用来管理自建 GPU 集群上的 Kubernetes 工作负载。Kubernetes 可以理解为一个调度员，你告诉它"我有这些 GPU 机器，帮我分配给不同的任务"，它来负责具体的分发、扩缩和故障处理。NVKE 做的事是在这个调度员上面再加一层，让你可以按需要开出多个独立的工作集群，每个集群有自己的控制中心，互不干扰。

我在意的是它的 README 里有一段话写得很坦率，原文大意是：API、配置和行为可能在版本之间变化，不建议用于生产工作负载。

这句话本身不稀奇，很多工具都写过类似的免责。让我停下来多想一秒的，是它后面还列出了几条更具体的限制：安装完成后，API 认证默认是关闭的，并且用的是明文 HTTP，需要操作者自行开启认证和访问保护，否则任何人都可以直接调用这个管理平面的接口。管理集群本身也不能自动升级、不能自我扩容，也没有备份或恢复流程。

这几条加在一起，说明的不是"还有些功能没做完"，而是"一旦你用这个工具，有些安全保障的责任在你自己"。这和你用一个功能还不完整的便利工具不是同一种情形。

## 先把限制看清，再决定用来做什么

预览版工具通常有两种用法是合理的：一是在本地或测试环境里摸索它的工作方式，看它的逻辑是否符合你的需求；二是参考它的代码思路，而不是直接部署。NVKE 的文档里也提供了不需要真实 GPU 硬件的本地快速启动，可以在 Linux 主机上用模拟节点跑起来，确认集群节点进入 Ready 状态。

这个本地模式有一个实际作用：让你在还没有真实硬件的情况下，先了解这套工具的操作方式，知道"管理平面"和"工作集群"在这里是什么关系，不用先投入机器成本。

不过，即使是评估目的的使用，默认关闭认证这件事依然需要注意。如果评估环境接了真实网络，没有手动开启认证的管理平面接口就相当于一个没有锁的门。文档里写了配置认证的入口，在用之前把这步做完，是最基本的动作。

有人可能会觉得，反正是评估，安全不是重点。这个想法有一个具体的风险：评估环境里的测试数据、调用记录，以及后续迁移到真实场景时可能沿用的配置，都可能因此暴露在本不该接触到它的地方。开源项目里写出这些限制，是在把判断的责任交还给使用者，不是告诉你"这些问题不用管"。

NVKE 目前使用 Apache 2.0 许可证，代码公开，版权属于 NVIDIA。由于目前处于预览状态，官方明确说不验证升级路径的稳定性，也不提供管理集群本身的升级方式。
