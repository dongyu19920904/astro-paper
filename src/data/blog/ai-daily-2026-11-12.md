Codex Security 的 README 里有一段话让我停了一下：扫描完成之后，它会生成一份报告，告诉你哪里有问题；但工具建议你在请求补丁之前，先读一遍报告里的"来源证据"和"排除范围"。

这让我在意的不是功能多不多，而是这个顺序。工具说"扫完先读报告，再让它改"，这和平时用 AI 的感觉不太一样。平时你让 AI 检查代码，它列一堆问题，你追问它直接就开始改了，自己说发现问题、自己说怎么修、自己动手。这里的逻辑是把"发现"和"修改"之间多放了一层，要求人来确认一次。

## 报告里的"来源证据"是什么

用日常话说，来源证据就是：这条漏洞来自代码里哪一行、哪一个函数，工具是从哪里推断出风险的。这件事听起来理所当然，但实际上很多自动扫描只告诉你"这里有问题"，不给你看它怎么判断的。

Codex Security 的报告会附上这条信息。这意味着你拿到结果的时候，不只是看一份清单，还能跟着它指的地方去确认：它说认证逻辑有问题，那段代码你自己看过一眼吗，它列出的证据让你信服吗。

排除范围同样值得看一遍。工具扫描时有覆盖不到的地方，比如它跳过了哪些路径、没有处理哪种类型的文件，报告里会写出来。这不是说工具不好，而是知道边界在哪里，你才知道这份扫描结果能说明什么、不能说明什么。

我在意这件事，是因为对刚开始用 AI 做代码相关工作的人，最容易踩的一步，不是工具没找到问题，而是工具找到了但你没有检查它对不对，就直接让它改了。改完的代码看起来没报错，但那条漏洞是不是真的存在过、改法是不是合适，你并不清楚。

## 修复这一步怎么接

扫描完成之后，你可以要求工具生成补丁，也可以先验证某条已有修复是否有效。工具把这两件事都做进去了：你可以让它自动生成修改，也可以告诉它"这个地方我已经改了，帮我确认有没有修好"。

这个区别对不经常处理安全问题的人来说有用：不是每次都从头改，有时候你已经改了一个地方，只是不确定改得够不够，可以单独拿去验证。

需要注意的是，工具的正式 README 里提到，某些类型的扫描结果需要特定的账户权限才能访问。如果你只是想先试试基本扫描，这部分限制暂时不影响你，但如果发现某些结果看不到，可以先查一下当前账户是否有对应访问权限，不必当成工具本身坏掉了。

工具支持在 CI/CD（就是自动跑构建和测试的流程）里使用，也支持单独在终端里手动扫一个仓库。两种方式用的是同一套扫描逻辑，只是触发方式不同。如果你还没搭自动化流程，直接在本地目录里跑一次也是可以的。
