有一件事值得停下来想：一个工具报出的问题越多，不一定代表它查得越仔细。有时候它是在用数量掩盖质量，或者根本就没看到某些文件。

open-code-review 的 README 里有一段话让我在意。它说自己和通用 AI 代理相比，精确率（Precision，可以理解成"报出来的问题有多少是真问题"）更高，但召回率（Recall，意思是"真正存在的问题它找到了多少"）更低。这是主动选择的权衡，不是偶然的结果。设计者的判断是：宁愿少报，也不要让你在一堆误报里翻来翻去。

这对我来说是个值得记住的区别。过去用 AI 检查什么，习惯性地觉得它说得越多越好，列得越长越可靠。但如果它报出的十条里有七条都是噪声，那份清单反而是在浪费你的时间，你还不知道哪条是真的。

## 它怎么做到少但准

这个工具的做法是把流程分成两层。

第一层是用工程代码（确定性的逻辑，不依赖大模型）决定哪些文件需要看、按什么顺序看、哪些文件要放在一起分析。比如一个功能涉及两个语言版本的配置文件，它会将这两个文件打包成一组交给模型，而不是分别扔进去各看一眼。这个捆绑动作是写死在代码里的，不靠模型临时判断。

第二层才是把每组文件送进大模型，让它从内容层面找问题。模型只负责判断，不负责决定看什么。

这样做的好处是第一层的覆盖范围是可预期的：哪些文件会进入审查、哪些会被过滤，工程逻辑决定，不会因为这次的提示词写法略有不同就漏掉几个文件。大模型的不稳定性被限制在了判断这一步，而不是蔓延到整个流程。

README 里提到了它在内部的一个基准测试数据，基于 50 个开源仓库、200 个真实的 Pull Request（代码合并请求），由 80 多位工程师标注了 1500 多个真实问题。这个基准是用来比较它和通用代理的差距的，不是对所有项目都适用的保证。工具在你自己项目上的表现，还是要自己测。

内置规则集的覆盖范围，根据说明包括几类常见的编码缺陷：空指针（NPE，程序试图访问一个不存在的对象时崩溃的典型原因）、线程安全（多任务并发执行时出现的数据冲突）、XSS（网页里注入恶意脚本）和 SQL 注入（通过输入框攻击数据库）。这些规则是预设的，不需要你自己写，但具体覆盖得多细，说明里读到的部分是截断的，细节有待查阅完整文档。

工具以命令行形式运行，可以接入 CI/CD 流水线（也就是每次提交代码时自动触发检查的那套机制），也支持接 OpenAI 和 Anthropic 的 API，用哪个模型由你配置决定。这里有一点要说清楚：它消耗的 token（模型计费的基本单位）根据 README 的说法大约是通用代理的九分之一，这是在它自己测试的条件下测出来的，实际费用还是取决于你的代码量和所用模型的定价。

我在意这个设计，是因为它的逻辑和常见的"让 AI 更聪明就能解决一切"不一样。它没有说要用更大的模型、更长的提示词，而是将流程里最不能出错的部分，交给不会犯迷糊的工程代码来保证。这是一种对大模型局限性的承认，也是一种更务实的用法。
