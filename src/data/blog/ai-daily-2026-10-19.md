DeepSeek 这次做的事情有点不一样。

[![来源配图：DeepSeek 推出搜索与网页提取 API · 原文封面](https://api-docs.deepseek.com/img/deepseek-social-card.jpeg)](https://api-docs.deepseek.com/guides/search/)

多数 AI 搜索能力是包在模型对话里的，你问模型一个问题，模型决定要不要搜索、搜什么，再把结果揉进回答。你拿到的是模型处理后的文字，原始搜索结果你不直接控制。

这次 DeepSeek 公布的是两个独立 JSON 接口：Search 直接返回网页搜索结果，Fetch 将指定 URL 提取为 Markdown。两者用同一套 API 密钥认证，不需要先调模型、再触发搜索。你完全可以在自己的代码里直接调这两个接口，拿到原始数据，再决定怎么处理。

这个区别对开发者意味着什么？

当搜索能力是模型的内部行为时，你很难在流程里精确控制它：搜索时机、搜索词、结果数量，都由模型决定。调试起来也麻烦，报错不知道出在搜索层还是生成层。独立接口的好处是职责清楚，搜索归搜索，生成归生成，可以分别测试、分别替换。

假设一个场景：你在构建一个需要实时信息的智能体，每次用户提问都要先拉几条近期结果，再交给语言模型处理。如果搜索耦合在模型里，整个链路很难拆开优化。用独立接口，你可以缓存搜索结果、控制调用频率、在结果不理想时换搜索词重试，不影响后续生成逻辑。

Fetch 接口也是类似的思路。让模型帮你读网页，模型会顺手做摘要、省掉你不想省的细节。Fetch 直接给你 Markdown，你自己决定取哪一段送进上下文，这样 token 用量更可预测。

费率目前是每千次成功请求 0.75 美元，只有成功返回且有结果时才计费。这个口径值得注意：空结果不收费，但"成功但结果为空"和"请求失败"在计费上可能是不同的，具体边界建议在接入前查看 API 文档的错误码说明，不要单靠这条对外宣传信息做预算。

有一个变化是 11 月 1 日起生效的：通过 Harness、Claude Code 或 Codex 调用时将按请求计费。这表明这些平台目前可能还在某种免费或捆绑计费状态，11 月之后行为会变。如果你的智能体工作流跑在这些工具里，11 月前值得确认一下当前的计费方式，避免成本突然变化。

我的判断是，独立搜索接口比包在模型对话里的搜索更适合有明确工程需求的场景，前提是你愿意自己管理搜索与生成之间的逻辑。如果你只是偶尔需要模型查一条信息，直接用支持搜索的对话模型反而更省事。接口的价值在于可控，但可控是有维护代价的。

在真正接入之前，有几件事值得先查清楚：Search 接口返回的结果结构（字段、数量上限、是否含正文片段还是只有摘要），Fetch 对 JS 渲染页面的支持情况，以及速率限制。这些细节决定它能不能替代你现有的搜索方案，光看定价和接口类型还不够。
